# Detective — Модель данных v2 («Слои и замки»)

> Технический документ к [DESIGN_DOC_V2.md](DESIGN_DOC_V2.md). Описывает формат файла дела (JSON), схему идентификаторов, состояние партии и сохранение, а также проверки загрузчика. Если этот документ расходится с диздоком, прав диздок, а этот документ нужно поправить.
>
> Как ИИ получает и обрабатывает эти данные (промпты, формат ответа, служебные проверки), описано в `AI_PROTOCOL_V2.md`; устройство кода — в `ARCHITECTURE_V2.md`.

---

## 1. Общие соглашения

- **Формат.** Одно дело — один файл JSON в UTF-8. Встроенные дела лежат в `res://cases/<id>.json`, пользовательские — в `user://cases/<id>.json`.
- **Имена полей** — английский `snake_case`. Тексты для игрока и ИИ — на языке дела (по умолчанию русский).
- **Идентификаторы** — строки из `a-z`, `0-9` и `_`, начинаются с буквы. Подробно — §3.
- **Обязательность.** Все поля обязательны, если не сказано иное. Пустой текст — `""`, пустой список — `[]`, отсутствие замка или условия — `null`.
- **Время** — строка `"HH:MM"` (24 часа). Подробно — §2.4.
- **Деревья условий** (замки слоёв и условия открытия улик) записываются одинаково:
  - лист — объект с полем `type`;
  - `{ "AND": [ ... ] }` — выполнены все элементы списка;
  - `{ "OR": [ ... ] }` — выполнен хотя бы один;
  - узлы вкладываются друг в друга, пустые `AND` и `OR` запрещены, одиночный лист пишется без обёртки.
- **Пометка «только для ИИ».** Поля, отмеченные в таблицах **ИИ**, игроку никогда не показываются: они идут только в промпт.

## 2. Файл дела

### 2.1. Корень

| Поле | Тип | Что это |
|---|---|---|
| `schema_version` | число, всегда `2` | Версия формата. Загрузчик v2 открывает только `2`. |
| `id` | id | Паспорт: стабильный идентификатор дела. По нему называется файл сохранения. |
| `title` | строка | Паспорт: название дела в списке дел и на экранах. |
| `briefing` | строка | Брифинг: завязка, жертва, обстоятельства. Видят игрок и ИИ-актёр. |
| `atmosphere` | строка | Атмосфера: стиль и тон дела. **ИИ**. |
| `time_window` | объект | Границы таймлайнов `t1`–`t2`, см. §2.4. |
| `starting_character_id` | id персонажа | С кого начинается расследование (выбран при первом входе). |
| `characters` | массив | Персонажи, §2.2. Порядок в массиве — порядок в списке персонажей. |
| `evidence` | массив | Улики, §2.6. Порядок — порядок на доске улик. |
| `conflicts` | массив | Авторский список конфликтов для ручной сборки несостыковок, §2.7. |
| `finale` | объект | Обвинение и финальный текст, §2.8. |

**Версия дела (хеш).** Отдельного поля в файле нет: версия — это SHA-256 от байтов файла дела. Загрузчик считает его при открытии, сохранение хранит его в `case_version_hash` (§5.1). Любая правка файла меняет хеш, и старое сохранение не загружается.

Экран брифинга дополнительно показывает список стартовых улик (улики с `open_condition: null`) и список участников (`name` и `role` всех персонажей) — эти списки берутся из `evidence` и `characters`, отдельных полей для них нет.

### 2.2. Персонаж (`characters[]`)

| Поле | Тип | Кто видит | Что это |
|---|---|---|---|
| `id` | id | — | Идентификатор персонажа. |
| `name` | строка | игрок, ИИ | Имя. |
| `gender` | `male` \| `female` | ИИ, движок | Пол: род в речи ИИ и подбор голоса. |
| `role` | строка | игрок, ИИ | Место в деле в 2–3 словах; подпись под именем. |
| `biography` | строка | **ИИ** | Краткая история жизни и характера. |
| `appearance` | строка | игрок, ИИ | Внешность: одежда, приметы, возраст. Карточка персонажа. |
| `behavior` | строка | игрок, ИИ | Как держится со стороны: осанка, жесты, мимика, привычки. Карточка персонажа. |
| `dialogue_goal` | строка | **ИИ** | Чего добивается и чего избегает в разговоре. |
| `speech_style` | объект | **ИИ** | Манера речи: `description` (строка) и `sample_lines` (массив строк, примеры реплик, можно `[]`). |
| `starting_emotion` | строка из списка эмоций | игрок, ИИ | Стартовая эмоция. Текущая эмоция живёт в состоянии партии (§4.4). |
| `attitude_to_investigator` | строка | **ИИ** | Позиция по отношению к следователю. Пока статична. |
| `profanity` | `never` \| `sometimes` \| `often` | **ИИ** | Уровень мата. |
| `greeting` | строка | игрок | Первая фраза при первой встрече. Говорит движок, а не ИИ. |
| `relationships` | массив | **ИИ** | Отношения к другим: `[{ "character_id": "...", "text": "..." }]`. Только своё восприятие. |
| `timeline` | массив | **ИИ** (через картину мира) | Таймлайн `t1`–`t2`: отрезки «где был» с вложенными «что делал» и точками-событиями, §2.4. |
| `facts` | массив | **ИИ** (через картину мира) | Вне-таймлайновые факты, §2.4. |
| `layers` | массив | **ИИ** (только активные, без замков) | Слои-легенды поверх скрытого, §2.5. |
| `voice` | объект | движок | Голос и филлеры: `tts_voice` (имя голоса TTS), `voice_style` (строка-подсказка стиля озвучки), `filler_lines` (массив коротких фраз-заполнителей; если `[]` — движок берёт стандартные «Хм…», «Ну…», «Секунду…»). |

**Список эмоций** (общий для `starting_emotion` и ответов ИИ): `calm`, `neutral`, `nervous`, `scared`, `sad`, `angry`, `controlled`, `contemptuous`.

Отдельного признака «подозреваемый / свидетель» нет: на механику он не влияет, а статус человека игрок понимает из `role` и брифинга.

### 2.3. Что ИИ-актёр получает из полей персонажа

ИИ-актёр получает `name`, `gender`, `role`, `biography`, `appearance`, `behavior`, `dialogue_goal`, `speech_style`, текущую эмоцию, `attitude_to_investigator`, `profanity`, `relationships`, а из `timeline`, `facts` и `layers` — только собранную кодом картину мира (§2.5.5). `greeting` и `voice` использует только движок. Замки (`lock`), неактивные слои, правда под активными слоями и чужие персонажи в промпт не попадают никогда.

### 2.4. Таймлайн и вне-таймлайновые факты

**Окно времени.** `time_window: { "start": "HH:MM", "end": "HH:MM" }` — общие для всего дела `t1` и `t2`. Если `end` меньше или равно `start`, окно переходит через полночь (например, `20:00`–`04:00`). Окно короче 24 часов. Все времена дела понимаются внутри окна: время меньше `start` — это следующие сутки. Для сравнения код переводит время в минуты от `start`.

**Отрезок «где был»** (`timeline[]`):

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор отрезка. Одновременно id показания (§3.2). |
| `from`, `to` | время | Начало и конец, `from` < `to`. |
| `place` | строка | Где был. |
| `notebook_important` | bool, по умолчанию `true` | Записывать ли в блокнот, когда персонаж это озвучил. |
| `activities` | массив, не пустой | Отрезки «что делал» внутри этого места. |

Отрезки «где был» идут по порядку, не пересекаются и покрывают окно от `start` до `end`.

**Отрезок «что делал»** (`activities[]`):

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор. Одновременно id показания. |
| `from`, `to` | время | Внутри своего отрезка «где был»; отрезки «что делал» идут по порядку, не пересекаются и покрывают его целиком. |
| `text` | строка | Чем занимался. |
| `notebook_important` | bool, по умолчанию `true` | Как выше. |
| `events` | массив | Точки-события внутри этого отрезка. |

**Точка-событие** (`events[]`):

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор. Одновременно id показания. |
| `time` | время | Момент события, в пределах `from`–`to` своего отрезка «что делал». |
| `text` | строка | Что произошло (кого увидел, с кем поссорился и т.п.). |
| `notebook_important` | bool, по умолчанию `true` | Как выше. |

**Вне-таймлайновый факт** (`facts[]`):

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор. Одновременно id показания. |
| `text` | строка | Сведение без привязки ко времени (долг, владение ключом, тайное знание). |
| `notebook_important` | bool, по умолчанию `true` | Как выше. |

Всё, что лежит в `timeline` и `facts`, — **правда** персонажа. Ложь задаётся только слоями (§2.5). Пересечения с другими персонажами автор описывает у обоих, каждого со своей стороны; общей хронологии дела нет.

**Текст записи в блокноте** собирается из полей, отдельного поля для него нет:
- «где был» — `"{from}–{to}: {place}"`;
- «что делал» — `"{from}–{to}: {text}"`;
- событие — `"{time}: {text}"`;
- факт — `"{text}"`.

### 2.5. Слои-легенды (`layers[]`)

Слои лежат плоским списком внутри персонажа. Вложенность задаётся ссылкой на слой, который лежит сверху.

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор слоя. Если легенда что-то утверждает (не просто скрывает), это и id её показания (§3.2). |
| `parent_layer_id` | id слоя или `null` | Слой, под которым лежит этот. `null` — верхний слой, активен с начала дела. |
| `target` | объект | Что прикрывает слой, §2.5.1. |
| `legend` | объект | Что персонаж утверждает вместо правды, §2.5.2. |
| `event_overrides` | массив | Только для `target.type` = `activity` или `place`: что происходит с событиями внутри, §2.5.2. Для `event` и `fact` поле не пишется. |
| `lie_motive` | строка | Мотив лжи: зачем персонаж держится этой версии. **ИИ**, только пока слой активен. |
| `notebook_important` | bool, по умолчанию `true` | Записывать ли легенду в блокнот, когда она прозвучала. |
| `lock` | дерево условий или `null` | Замок, §2.5.3. `null` — неснимаемый слой. |

#### 2.5.1. Цель слоя (`target`)

| `type` | Поля | Что прикрывает |
|---|---|---|
| `event` | `event_id` | Одну точку-событие. |
| `activity` | `activity_ids` (не пустой) | Один или несколько соседних отрезков «что делал» внутри **одного** отрезка «где был», по порядку. |
| `place` | `place_ids` (не пустой) | Один или несколько соседних отрезков «где был», по порядку. Вместе с ними прикрыты все их «что делал». |
| `fact` | `fact_id` | Один вне-таймлайновый факт. |

Все ссылки — на элементы таймлайна или факты **этого же** персонажа.

**Охват слоя** — множество элементов, которые он прикрывает:
- `event` — само событие;
- `activity` — отрезки «что делал» и все события внутри них;
- `place` — отрезки «где был», все их «что делал» и все события;
- `fact` — сам факт.

#### 2.5.2. Содержимое легенды (`legend`) и события внутри

Форма `legend` зависит от `target.type`:

| `target.type` | `legend` | Смысл |
|---|---|---|
| `event` | `{ "mode": "replace", "text": "..." }` или `{ "mode": "hide" }` | Подменить событие другим или скрыть его. Время подменённого события — время исходного. |
| `fact` | `{ "mode": "replace", "text": "..." }` или `{ "mode": "hide" }` | Подменить факт или скрыть его. |
| `activity` | `{ "text": "..." }` | Чем, по словам персонажа, он занимался на всём промежутке прикрытых отрезков (от `from` первого до `to` последнего). |
| `place` | `{ "place": "...", "activity": "..." }` | Где, по словам персонажа, он был и что делал на всём промежутке прикрытых отрезков. «Что делал» подменяется автоматически вместе с местом. |

Для `activity` и `place` автор обязан явно решить судьбу **каждого** события в охвате — через `event_overrides`:

```json
{ "event_id": "...", "mode": "keep" }
{ "event_id": "...", "mode": "hide" }
{ "event_id": "...", "mode": "replace", "statement_id": "...", "text": "..." }
```

- `keep` — событие остаётся правдой и видно ИИ;
- `hide` — событие скрыто;
- `replace` — вместо события персонаж утверждает другое; у подменённого события свой id показания `statement_id` и время исходного события.

Слой в режиме `hide` ничего не утверждает: у него нет показания, и `notebook_important` на нём не используется.

Тексты записи в блокноте для легенд:
- `place` — `"{from}–{to}: {legend.place} — {legend.activity}"`;
- `activity` — `"{from}–{to}: {legend.text}"`;
- `event` / подменённое событие — `"{time}: {text}"`;
- `fact` — `"{text}"`.

#### 2.5.3. Замок (`lock`)

Дерево условий (§1) с двумя типами листьев:

```json
{ "type": "evidence", "evidence_id": "ev_pass_log", "require_show": true }
{ "type": "statement", "statement_id": "oleg_e_saw_anna" }
```

- `evidence` — улика, уже открытая игроком. `require_show` (bool, по умолчанию `false`) — галочка «требовать предъявить»: если `true`, устное упоминание условие не выполняет, персонаж требует показать улику, и засчитывается только предъявление через интерфейс (с доски или в составе несостыковки).
- `statement` — свидетельское показание **другого** персонажа, которое игрок уже услышал и которое записано в блокноте (статус «услышано» или «опровергнуто», §4.2). У показаний флага `require_show` нет: они засчитываются и кнопкой «Пересказать», и устно.

`lock: null` — слой не снимается никогда.

**Ключ условия** — строка, по которой код запоминает выполненные листья: `evidence:<evidence_id>` или `statement:<statement_id>`. Один и тот же лист, встречающийся в замке дважды, — одно условие.

#### 2.5.4. Вложенность и активные слои

- Слой **активен**, если он ещё не снят и либо верхний (`parent_layer_id: null`), либо его родитель уже снят.
- Слои снимаются строго сверху вниз: снять можно только активный слой.
- Под снятым слоем открывается то, что лежит в его охвате: дочерние слои (они становятся активными) или правда — там, где дочерних слоёв нет.
- Охват дочернего слоя лежит внутри охвата родителя (может совпадать с ним — так задаётся вторая легенда на то же самое).
- Два слоя с пересекающимся охватом допустимы, только если один из них — предок другого. Поэтому в любой момент каждый элемент прикрыт не больше чем одним активным слоем.

#### 2.5.5. Картина мира персонажа

Картину мира, которую видит ИИ-актёр, код собирает из данных и списка снятых слоёв так:

1. Находит активные слои.
2. Для каждого элемента `timeline` и `facts`:
   - если элемент не входит в охват ни одного активного слоя — он виден как правда;
   - если входит — вместо него видна легенда активного слоя по правилам §2.5.2 (место и/или «что делал» подменены, события по `event_overrides` оставлены, подменены или скрыты, событие или факт подменены или скрыты целиком).
3. К каждой активной легенде добавляет её `lie_motive`.

Правда под активными слоями, нижние слои, замки и `lie_motive` неактивных слоёв в картину не попадают. Смысловую согласованность соседних слоёв (чтобы раскрытая правда в одном месте не выдавала то, что прикрыто другим слоем) обеспечивает автор.

### 2.6. Улика (`evidence[]`)

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор. |
| `title` | строка | Название на доске и в уведомлениях. |
| `type` | `document` \| `item` \| `place` | Документ, предмет или место/осмотр. |
| `short_description` | строка | Строка для списка на доске. |
| `full_text` | строка | Полный текст: читает игрок, видит ИИ после предъявления. |
| `mention_hint` | строка, необязательно | Подсказка служебной проверке, как персонаж может назвать улику в речи («журнал пропусков, отметки на двери»). Игроку и ИИ-актёру не показывается. |
| `open_condition` | дерево условий или `null` | `null` — стартовая улика. Иначе — дерево из листьев `{ "type": "mentioned_by", "character_id": "..." }`: улика открывается, когда нужные персонажи прямо на неё указали. `OR` — хватит любого из них, `AND` — нужны все (указания копятся между ходами и персонажами). |

Снятие слоя улику не открывает. Улику открывает только её `open_condition`.

### 2.7. Конфликты для несостыковок (`conflicts[]`)

Автоматических противоречий в игре нет. Автор перечисляет пары записей, которые действительно конфликтуют; игрок сам выбирает две записи в блокноте, и код ищет пару в этом списке.

| Поле | Тип | Что это |
|---|---|---|
| `id` | id | Идентификатор конфликта и собранной несостыковки. |
| `a`, `b` | объект `{ "type": "statement" \| "evidence", "id": "..." }` | Две стороны конфликта. Допустимо: показание + показание разных персонажей или показание + улика. Две улики — нельзя. |
| `description` | строка | Короткое объяснение, которое игрок видит в блокноте после сборки. |

Порядок сторон не важен: пара `(a, b)` совпадает с выбором `(b, a)`.

### 2.8. Финал (`finale`)

Временный вариант финала: выбор из вариантов, верные пункты накапливаются, попытки не ограничены.

| Поле | Тип | Что это |
|---|---|---|
| `killer_id` | id персонажа | Верный убийца. Варианты для выбора — все персонажи дела. |
| `motive_options` | массив `{ "id", "text" }` | Варианты мотива, не меньше двух. |
| `correct_motive_id` | id из `motive_options` | Верный мотив. |
| `method_options` | массив `{ "id", "text" }` | Варианты способа, не меньше двух. |
| `correct_method_id` | id из `method_options` | Верный способ. |
| `final_text` | строка | Развязка: показывается на экране победы. ИИ её не видит. |

При каждой попытке обвинения каждый верно выбранный пункт (убийца, мотив, способ) отмечается навсегда. Дело раскрыто, когда отмечены все три.

## 3. Идентификаторы и ссылки

### 3.1. Правила

- Все id в деле — **уникальны на всё дело**, независимо от коллекции: персонажи, отрезки, события, факты, слои, `statement_id` подменённых событий, улики, конфликты, варианты мотива и способа. Одно пространство имён упрощает ссылки и сообщения валидатора.
- Формат: `^[a-z][a-z0-9_]*$`.
- id не меняются при правке текстов: сохранение ссылается на них. (Любая правка файла всё равно меняет хеш дела, §2.1.)
- Рекомендуемые префиксы (не обязательны): `<персонаж>_p_…` — «где был», `<персонаж>_a_…` — «что делал», `<персонаж>_e_…` — событие, `<персонаж>_f_…` — факт, `<персонаж>_l_…` — слой, `<персонаж>_s_…` — подменённое событие, `ev_…` — улика, `c_…` — конфликт, `m_…` / `w_…` — мотив и способ.

### 3.2. Показания (statement)

**Показание** — любая единица, которую персонаж может произнести и которая может попасть в блокнот. id показания — это id одного из элементов:

| Источник | id показания | Чьё показание |
|---|---|---|
| отрезок «где был» | `timeline[].id` | персонажа-владельца |
| отрезок «что делал» | `activities[].id` | то же |
| событие | `events[].id` | то же |
| факт | `facts[].id` | то же |
| легенда слоя (кроме режима `hide`) | `layers[].id` | то же |
| подменённое событие в `event_overrides` | `statement_id` | то же |

Каждое показание принадлежит ровно одному персонажу. Код строит таблицу `statement_id → { character_id, источник, текст для блокнота, слой (если это легенда) }` при загрузке.

### 3.3. Кто на что ссылается

| Откуда | Поле | Куда |
|---|---|---|
| корень | `starting_character_id` | персонаж |
| `relationships[]` | `character_id` | другой персонаж |
| `layers[]` | `parent_layer_id` | слой того же персонажа |
| `layers[].target` | `event_id` / `activity_ids` / `place_ids` / `fact_id` | элементы того же персонажа |
| `event_overrides[]` | `event_id` | событие в охвате слоя |
| лист замка `evidence` | `evidence_id` | улика |
| лист замка `statement` | `statement_id` | показание другого персонажа |
| лист `mentioned_by` | `character_id` | персонаж |
| `conflicts[].a/.b` | `id` | показание или улика (по `type`) |
| `finale` | `killer_id`, `correct_motive_id`, `correct_method_id` | персонаж, вариант мотива, вариант способа |

## 4. Состояние партии

Состояние партии — всё, что меняется во время игры. Данные дела в нём не дублируются: состояние хранит только id и то, чего нет в файле дела.

### 4.1. Корень состояния

| Поле | Тип | Что это |
|---|---|---|
| `status` | `in_progress` \| `solved` | Статус дела. «Не начато» — когда сохранения нет. |
| `turn` | число | Счётчик ходов игрока (для порядка записей). |
| `current_character_id` | id персонажа | С кем сейчас разговор. |
| `opened_evidence` | массив id улик | Открытые улики в порядке открытия (стартовые — сразу). |
| `evidence_mentions` | словарь `evidence_id → [character_id]` | Кто уже прямо указал на ещё закрытую улику — накопление для `AND` в `open_condition`. |
| `notebook` | объект | Блокнот, §4.2. |
| `characters` | словарь `character_id → объект` | Состояние каждого персонажа, §4.3. |
| `accusation` | объект | Обвинение, §4.5. |
| `badges` | объект | Индикаторы нового, §4.6. |

### 4.2. Блокнот (`notebook`)

```json
"notebook": {
  "statements": [
    { "statement_id": "oleg_e_saw_anna", "character_id": "oleg", "heard_turn": 3, "status": "heard" }
  ],
  "inconsistencies": [
    { "conflict_id": "c_anna_room_vs_oleg", "assembled_turn": 7 }
  ]
}
```

- **Показания** (`statements`). Запись появляется, когда служебная проверка после ответа отметила, что персонаж озвучил элемент своей текущей картины мира с `notebook_important: true`. Одно показание записывается один раз. Записи группируются по `character_id`.
- **Статусы**: `heard` — услышано; `refuted` — опровергнуто. Когда слой снимается, все уже записанные показания этого слоя (легенда слоя и его подменённые события) получают `refuted`. Запись не удаляется. Новые показания, открывшиеся под слоем, записываются как `heard`, когда персонаж их озвучит.
- Для замков и пересказа годятся записи в любом статусе: игрок эти слова действительно слышал.
- **Несостыковки** (`inconsistencies`). Игрок выбирает две стороны: записи из `statements` и/или открытые улики. Если пара есть в `conflicts`, в список добавляется `conflict_id` (повторно — не добавляется). Если нет — мягкое сообщение, состояние не меняется.

### 4.3. Состояние персонажа (`characters[id]`)

| Поле | Тип | Что это |
|---|---|---|
| `greeted` | bool | Первая фраза уже прозвучала. |
| `emotion` | строка из списка эмоций | Текущая эмоция (с начала — `starting_emotion`). |
| `removed_layers` | массив id слоёв | Снятые слои в порядке снятия. Активные слои вычисляются из этого списка (§2.5.4). |
| `lock_progress` | словарь `layer_id → [ключи условий]` | Накопленные выполненные условия замков, §4.4. |
| `memory` | объект | Память о диалоге, §4.4. |
| `log` | массив | Лента диалога для экрана: реплики игрока и персонажа (с эмоцией и ремаркой) и служебные уведомления. В промпт не идёт. |

### 4.4. Замки и память о диалоге

**Накопление условий.** Когда игрок что-то предъявляет текущему персонажу (улику, пересказ показания, несостыковку или устное упоминание, которое подтвердил судья), код:

1. Определяет, какие ключи условий выполнены этим действием:
   - улика через интерфейс → `evidence:<id>` (выполняет лист при любом `require_show`);
   - улика устно → `evidence:<id>`, но только для листьев с `require_show: false`; если лист требует предъявления, ключ не засчитывается, а в событие хода идёт сигнал «потребовать показать улику»;
   - пересказ показания (кнопкой или устно) → `statement:<id>`;
   - несостыковка → ключи обеих сторон; улика в составе несостыковки считается предъявленной через интерфейс.
   Устно засчитываются только уже открытые улики и уже записанные в блокнот показания.
2. Добавляет эти ключи в `lock_progress` **каждого активного** слоя этого персонажа, в замке которого есть такой лист.
3. Вычисляет дерево замка по накопленным ключам. Если оно выполнено — слой добавляется в `removed_layers`, его записи в блокноте получают `refuted`, в память пишется снятая легенда.

`lock_progress` хранится в сохранении и не сбрасывается при переключении на других персонажей. Частичный прогресс ИИ не видит.

**Память о диалоге** (`memory`):

| Поле | Тип | Что это |
|---|---|---|
| `refuted_legends` | массив `{ "layer_id", "caught_by": [ключи условий] }` | Снятые легенды: «раньше утверждал X (текст легенды из дела), поймали на Y (тексты улик и показаний по ключам)». |
| `shown_evidence` | массив id улик | Улики, которые этому персонажу уже предъявляли (через интерфейс, устно или в составе несостыковки). Полные тексты берутся из дела. |
| `retold_statements` | массив id показаний | Чужие показания, которые ему пересказали. |
| `presented_conflicts` | массив id конфликтов | Несостыковки, которые ему предъявляли. |
| `summary` | строка | Сжатая выжимка старых реплик: как отбивался, какие детали назвал, что ему пересказали. |
| `recent` | массив `{ "speaker": "player" \| "character", "text" }` | Последние 4 реплики дословно. |
| `unsummarized` | массив того же вида | Реплики, вытесненные из `recent` и ещё не вошедшие в `summary`. Когда их набирается достаточно, запускается сжатие (порог — в `AI_PROTOCOL_V2.md`), после чего список очищается. |

### 4.5. Обвинение (`accusation`)

```json
"accusation": { "killer_found": false, "motive_found": false, "method_found": false, "attempts": 0 }
```

Флаги только включаются. Когда все три `true`, `status` становится `solved`, и игроку показывается `final_text`.

### 4.6. Индикаторы нового (`badges`)

```json
"badges": { "evidence": ["ev_pass_log"], "notebook": ["oleg_e_saw_anna"] }
```

- `evidence` — открытые, но ещё не просмотренные улики. Очищается, когда игрок открывает вкладку «Улики» (или карточку улики).
- `notebook` — новые записанные показания. Очищается, когда игрок открывает вкладку «Блокнот».

Уведомления в ленте (открыта улика, предъявлена улика / пересказ / несостыковка) пишутся в `log` текущего персонажа.

## 5. Сохранение и настройки

### 5.1. Файл сохранения

Одно сохранение на дело: `user://saves/<case_id>.json`. Пишется после каждого хода и при сворачивании приложения.

```json
{
  "format": 2,
  "case_id": "library_night",
  "case_version_hash": "<sha256 файла дела>",
  "saved_at": "2026-11-28T10:15:00+01:00",
  "state": { }
}
```

- `state` — состояние партии из §4.
- Сохранение не загружается, если `format` не `2`, `case_id` не совпал или `case_version_hash` не равен хешу текущего файла дела. Тогда показывается экран «Дело повреждено / устарело» с кнопкой начать заново.
- «Начать заново» удаляет файл сохранения этого дела.
- Статус в списке дел: нет сохранения — «не начато», `in_progress` — «в процессе», `solved` — «раскрыто».

### 5.2. Настройки отдельно от партии

Настройки лежат в `user://config.cfg` и не зависят от дела: озвучка (TTS) и филлеры, распознавание речи (Gemini / Parakeet) и загруженная модель, режим микрофона и длительность паузы, масштаб текста, API-ключ, счётчик расходов. В файл сохранения они не попадают, а удаление или сброс сохранения их не трогает. API-ключ никогда не пишется в сохранение.

## 6. Проверки загрузчика

Загрузчик проверяет дело до начала игры. **Ошибка** — дело не открывается, игроку и автору показывается список ошибок с id элементов. **Предупреждение** — дело открывается, предупреждение пишется в лог (и показывается в редакторе).

### 6.1. Ошибки

**Структура**
1. `schema_version` равен `2`; все обязательные поля есть и нужного типа; обязательные строки (`title`, `briefing`, `name`, `role`, `place`, `text`, `full_text`, `final_text` и т.п.) не пустые.
2. Значения из списков допустимы: `gender`, `profanity`, `starting_emotion`, `evidence.type`, `legend.mode`, `event_overrides[].mode`, `target.type`, типы листьев.
3. Все id соответствуют формату и уникальны на всё дело.

**Ссылки**
4. Нет висячих ссылок: каждая ссылка из таблицы §3.3 указывает на существующий элемент нужного вида.
5. `relationships`: нет ссылки на себя и повторов одного персонажа.
6. В деле есть хотя бы один персонаж; `starting_character_id` существует.

**Таймлайн**
7. Время в формате `HH:MM`; `time_window` короче 24 часов.
8. Отрезки «где был» идут по порядку, не пересекаются, `from` < `to`, лежат внутри окна. Отрезки «что делал» лежат внутри своего «где был», идут по порядку и не пересекаются. События лежат внутри своего «что делал».

**Слои**
9. `target` ссылается на элементы своего персонажа; `activity_ids` — соседние отрезки внутри одного «где был», по порядку; `place_ids` — соседние отрезки по порядку; списки без повторов.
10. Форма `legend` соответствует `target.type` (§2.5.2). Для `activity` и `place` в `event_overrides` перечислено **каждое** событие охвата ровно один раз и ничего лишнего; у `replace` есть `statement_id` и `text`. Для `event` и `fact` поля `event_overrides` нет.
11. `parent_layer_id` — слой того же персонажа; цепочки родителей без циклов.
12. Охват дочернего слоя лежит внутри охвата родителя. Слои с пересекающимся охватом — только предок и потомок.

**Замки**
13. В замке нет пустых `AND`/`OR`; листья только `evidence` и `statement`; `require_show` есть только у листа `evidence`.
14. Лист `statement` ссылается на показание **другого** персонажа; это показание имеет `notebook_important: true` и не является слоем в режиме `hide`.
15. **Достижимость (и отсутствие циклов между замками).** Код моделирует прохождение: считает открытыми все улики (стартовые и с `open_condition`), доступными — все показания текущих картин мира и затем по кругу снимает каждый слой, чей замок выполним из доступного, добавляя открывшиеся показания, пока что-то меняется. Каждый слой с замком в итоге должен сняться. Не снялся — ошибка «замок недостижим»: условие лежит под неснимаемым слоем, требует показание, которое откроется только после снятия этого же слоя, или два замка ждут друг друга.

**Улики**
16. `open_condition` — `null` или дерево только из листьев `mentioned_by` с существующими `character_id`.
17. Есть хотя бы одна стартовая улика.

**Конфликты**
18. У конфликта хотя бы одна сторона — показание; две стороны-показания принадлежат разным персонажам; стороны-показания имеют `notebook_important: true` и достижимы по правилу 15; одна и та же пара (без учёта порядка) не повторяется.

**Финал**
19. `killer_id` — существующий персонаж; в `motive_options` и `method_options` не меньше двух вариантов без повторов id; `correct_motive_id` и `correct_method_id` есть среди своих вариантов; `final_text` не пустой.

### 6.2. Предупреждения

1. Персонаж без `greeting`.
2. Открываемая (не стартовая) улика, которая не используется ни в одном замке и ни в одном конфликте.
3. Слой с `lock: null`, под которым есть дочерние слои (они никогда не станут активными).
4. Персонаж, у которого нет ни одного показания с `notebook_important: true`.
5. Улика с `open_condition`, у которой нет `mention_hint`.

## 7. Пример: мини-дело «Ночь в библиотеке»

Выдуманное учебное дело на трёх персонажей. Показывает все виды данных: отрезки, события и факты; слои на место, на «что делал» (вложенный) и на факт; неснимаемый слой; замки `AND` и одиночный лист, оба типа условий и галочку `require_show`; стартовые и открываемые улики с `OR`; конфликты; финал.

Цепочка решения: Олег рассказывает, что видел Анну у архива, и указывает на журнал пропусков → игрок предъявляет Анне показание Олега и журнал (замок `AND`, журнал нужно показать) → Анна признаёт, что была в архиве, но говорит о падении → Вера указывает на пропавшее пресс-папье → предъявление пресс-папье снимает легенду о падении. ## 8. Открытые вопросы

1. **Условия для нижних слоёв.** В этом документе условия засчитываются только активным слоям (§4.4): если игрок предъявил улику из замка нижнего слоя, пока верхний не снят, она не запоминается, и после снятия верхнего слоя её придётся предъявить ещё раз. В том числе это касается несостыковки, которая за одно предъявление снимает верхний слой и при этом содержит условие для открывшегося под ним. Диздок говорит только о том, что «выполненные условия запоминаются в замке», и не уточняет, копятся ли они для ещё неактивного слоя. Нужно решить, оставить ли так или засчитывать условия заранее.
