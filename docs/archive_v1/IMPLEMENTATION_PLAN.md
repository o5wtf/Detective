# План реализации прототипа

Каждый этап — одна задача для Cursor (облачного агента) и один пулл-реквест. Этапы идут строго по порядку: следующий опирается на предыдущий. Этап считается сделанным, когда выполнены **все** критерии приёмки и тесты проходят командой:

```
godot --headless --path . -s res://tests/run_tests.gd
```

Документы, на которые опираются этапы:
- `Дизайн документ Игры` — диздок, ссылки вида «Д§8»;
- `docs/ARCHITECTURE.md` — «А§3.2»;
- `docs/LLM_PROTOCOL.md` — «П§6»;
- `docs/UI_PROTOTYPE.md` — «UI§2.4».

Общие правила для всех этапов:
- Godot 4.7.x, GDScript со статической типизацией, без сторонних аддонов.
- Не менять диздок, `cases/*.json` и `tools/validate_case.py` без явной просьбы. Если нашлось противоречие в документах — остановиться и описать его в пулл-реквесте.
- Тестовые имена и сообщения могут ссылаться на тестовое дело. Спойлеры в тестах допустимы.
- `cases/*_NOTES.md` не читать: там заметки автора, для реализации они не нужны.

## Этап 1. Скелет проекта и раннер тестов

**Цель.** Пустой проект Godot, который открывается в редакторе, и работающие headless-тесты.

**Файлы:**
- `project.godot` (имя «Detective», главная сцена-заглушка);
- `.gdignore` в `docs/` и `tools/`;
- папки из А§2 с пустыми `.gitkeep`;
- автозагрузки-заглушки `src/autoload/game.gd` и `src/autoload/llm.gd`;
- `tests/run_tests.gd` (раннер, `extends SceneTree`), `tests/test_case.gd` (базовый класс с `assert_eq`, `assert_true`, `assert_false`, `assert_has`, `fail`), `tests/test_smoke.gd`;
- `config/config.example.cfg` по П§8.

**Следовать:** А§1, А§2, А§8.

**Приёмка:**
- Раннер находит все `tests/test_*.gd`, запускает методы `test_*`, в том числе асинхронные (с `await`).
- Печатает «PASS/FAIL имя» и итог.
- Код выхода 0, если всё прошло, и 1, если что-то упало. Проверить временным падающим тестом, потом убрать.
- `test_smoke.gd` проверяет, что автозагрузки `Game` и `LLM` существуют.
- Проект открывается в Godot 4.7 без ошибок в консоли.

**Не делать:** логику дела, UI, сеть.

## Этап 2. Загрузка и валидация дела

**Цель.** `CaseLoader` и `CaseValidator` с теми же правилами, что `tools/validate_case.py`.

**Файлы:**
- `src/core/case_data.gd`, `src/core/case_loader.gd`, `src/core/case_validator.gd`, `src/core/conditions.gd` (только проверка синтаксиса условий);
- `tests/test_case_validator.gd`;
- `tests/fixtures/valid_minimal.json` и 12–15 файлов `tests/fixtures/broken_*.json`, каждый ломает **одно** правило. Обязательно покрыть: убийцы нет; мотива нет в списке; ложь без `lie_text`; `cannot_lie` с `lie_text`; `pressure_for_full < pressure_for_basic`; неизвестная улика в факте; неизвестный агент в условии; пустой `OR`; противоречие на несуществующий факт; форма `lie` у факта без лжи; `breaks_lie_on` со значением `contradiction` без противоречия; эмоция не из списка; нет `prompt_background`; ключевая улика без фактов.
- `tests/fixtures/manifest.json`: для каждого файла — сколько ошибок выдаёт `python3 tools/validate_case.py <файл>`. Заполнить, реально запустив Python-скрипт.

**Следовать:** Д§2, Д§7, Д§8 (валидация фактов), Д§13, Д§14, Д§15; А§3.1. Источник правды по правилам — `tools/validate_case.py`.

**Приёмка:**
- `cases/rain_over_shadow.json` загружается без ошибок.
- Каждый `broken_*` отклоняется, у ошибки ожидаемый код. Число ошибок совпадает с `manifest.json` (то есть с Python).
- Сломанный JSON (синтаксис) даёт понятную ошибку, а не падение.

**Не делать:** механику раскрытия фактов, давления и так далее.

## Этап 3. Движок правил (RulesEngine)

**Цель.** Вся механика без UI и без модели.

**Файлы:**
- `src/core/rules_engine.gd`, `src/core/game_state.gd`, `src/core/balance.gd`, `src/core/conditions.gd` (вычисление условий), `src/core/accusation.gd`;
- `tests/test_rules_engine.gd`, `tests/helpers/sim_harness.gd`;
- `tests/golden/rain_over_shadow_sim_0.json` и `..._sim_15.json`, сделанные командой:
  ```
  python3 tools/validate_case.py cases/rain_over_shadow.json --simulate 0 --json > tests/golden/rain_over_shadow_sim_0.json
  python3 tools/validate_case.py cases/rain_over_shadow.json --simulate 15 --json > tests/golden/rain_over_shadow_sim_15.json
  ```

**Следовать:** Д§3, Д§4, Д§5, Д§8, Д§11 (таблица баланса), Д§14, Д§15; А§3.2, А§3.3 (порядок каскада обязателен).

**Приёмка:**
- **Модульные тесты на маленьких фикстурах:**
  - Basic/Full по порогам;
  - `requires_evidence`;
  - `must_lie` не отдаёт правду до слома;
  - `can_lie` даёт `lie_or_basic` после порога Basic;
  - `breaks_lie_on` списком (любое из);
  - слом лжи открывает минимум Basic;
  - каждая пара «улика — агент» даёт давление один раз;
  - противоречие с уже сломанной ложью давления не даёт;
  - противоречие без лжи даёт +5 обоим;
  - давление ограничено 0–100;
  - все типы условий и `AND`/`OR`;
  - найденное противоречие запоминает ход; старый список id загружается без этого поля;
  - обвинение: неверный убийца — мотив и способ не оцениваются; галочки сохраняются.
- **Совпадение с эталоном:** `sim_harness` повторяет симуляцию Python (тон добавляется к стартовому давлению; поговорить со всеми; каждую открытую улику показать каждому агенту; «услышать» каждое доступное утверждение, ложь — с самого начала, оговорки не считаются; повторять до стабильности). Итоговые уровни фактов, открытые улики, противоречия, сломанная ложь и давление совпадают с golden-файлами для тона 0 и 15.
- `GameState.to_dict()` → `from_dict()` даёт то же состояние.

**Не делать:** промпты, сеть, UI.

## Этап 4. Состояние диалога и сборка промпта (с моком модели)

**Цель.** Промпт хода и схема ответа строго по протоколу. Проверяется на `MockLLMClient`.

**Файлы:**
- `src/dialogue/dialogue_state.gd`, `src/dialogue/prompt_builder.gd`, `src/dialogue/summarizer.gd`, `src/dialogue/evidence_matcher.gd`;
- `src/llm/llm_client.gd`, `src/llm/mock_llm_client.gd`;
- `tests/test_prompt_builder.gd`, `tests/test_dialogue_state.gd`, `tests/test_evidence_matcher.gd`.

**Следовать:** Д§9, Д§13; П§3, П§4, П§5, П§7; А§3.4, А§3.5, А§3.9.

**Приёмка:**
- Шаблоны промптов совпадают с П§3–П§4 (проверка по ключевым строкам).
- **В промпте никогда нет:**
  - `background`, `truth_timeline`, `killer_id`;
  - текстов закрытых фактов;
  - `content_full` для фактов уровня Basic;
  - правды по несломанной `must_lie`.

  Тест перебирает всех агентов тестового дела на нескольких состояниях движка.
- В схеме ответа перечни `enum` содержат ровно ключи текущего пакета и открытых улик (`["none"]`, если пусто).
- Окно 6 реплик; `needs_summary()` срабатывает ровно по правилу П§7. Запасное резюме без модели работает.
- `EvidenceMatcher` находит улику по названию в разных падежах (тест на 3–4 примерах).

**Не делать:** настоящие HTTP-запросы, UI.

## Этап 5. Клиент Gemini

**Цель.** Настоящие запросы к Gemini и аккуратная обработка ошибок.

**Файлы:**
- `src/llm/gemini_client.gd`, `src/llm/llm_config.gd`, `src/autoload/llm.gd` (выбор `gemini` или `mock` по настройкам);
- `tests/test_gemini_client.gd` с подменённым транспортом: HTTP-слой выделен в маленький класс, который в тесте заменяется фейком;
- `tests/manual/gemini_smoke.gd` — ручная проверка одним запросом, запускается только при наличии ключа.

**Следовать:** Д§12; П§2, П§8; А§3.6, А§6.

**Приёмка:**
- Тело запроса совпадает с П§2.2: `systemInstruction`, `responseMimeType`, `responseJsonSchema`, `thinkingConfig`, `safetySettings`. Модели берутся из настроек.
- **Разбор ответа:** части с `thought` пропускаются; `finishReason` и `blockReason` переводятся в коды ошибок по П§2.3.
- **Ошибки (тесты на фейковом транспорте):** 429 и 503 повторяют ту же модель, 401/403, 500, таймаут, нет сети, битый JSON. Другую модель клиент не выбирает.
- Паузы между запросами нет; в полёте не больше одного запроса.
- **Ключ:** читается из `user://config.cfg`, затем из `GEMINI_API_KEY`, затем (только в отладке) из `res://config/dev.cfg`. Ключа нет в логах.
- `gemini_smoke.gd` с настоящим ключом получает корректный JSON по схеме (проверяет человек, результат приложить в описание пулл-реквеста).

**Не делать:** UI, голос.

**Цель.** Партию можно закончить, прервать и продолжить.

**Файлы:**
- `src/save/save_state.gd`; доработка `accusation.tscn` и экрана победы; «Продолжить» и «Начать заново» в меню;

- Галочки обвинения сохраняются между попытками и после перезапуска.

## Этап 9. Экспорт под Android-планшет и Windows

**Цель.** Рабочие сборки.

**Файлы:** `export_presets.cfg` (Android arm64, Windows x86_64; Linux и macOS не нужны); `docs/BUILD.md` — как собрать и подписать (отладочный ключ подписи Android **не** коммитить).

**Следовать:** Д§12; А§6.

**Приёмка:**
- Android: разрешение `INTERNET` включено; `cases/*.json` попадают в сборку (фильтр не-ресурсных файлов); `config/dev.cfg`, `docs/`, `tools/` — не попадают.
- В собранном пакете нет ключа API: проверить поиском строки по `.pck` или `.apk`.
- Android: ориентация `sensor`, в манифесте поддержка больших экранов; APK ставится на планшет.
- Ручная проверка на Android-планшете в обеих ориентациях: ввести ключ, допросить, предъявить улику, отметить противоречие, повернуть экран посреди допроса, свернуть и развернуть приложение, продолжить сохранение; клавиатура не закрывает поле ввода.
- Сборка для Windows (`.exe` + `.pck` или один файл) запускается и проходит те же шаги мышью и клавиатурой.

**Не делать:** публикацию в магазинах, свой сервер для ключа.

## Будущие этапы (после прототипа)

### Этап 10. Голос

Этап O1 уже сделан отдельно: системная озвучка без микрофона, `SpeechBackend` и очередь в `src/voice/`. Распознавание речи и облачный синтез из этого этапа в O1 не входят.

**Цель.** Агенты говорят голосом, игрок может спрашивать голосом. По умолчанию облачный голос, в настройках — переключение на встроенный голос устройства.

**Перед началом:** выбрать облачного поставщика (открытый вопрос диздока, раздел 12). Сравнить 2–3 кандидата с бесплатным уровнем на одних и тех же 10 русских репликах; первым проверить Gemini TTS — тот же ключ.

**Файлы:** `src/voice/*` из А§2, блок «Голос» в настройках, кнопка микрофона в допросе; `tests/test_voice_provider.gd` (с фейковым транспортом и фейковым микрофоном).

**Следовать:** Д§10, Д§12; А§3.12; UI§2.1, UI§2.4.

**Приёмка:**
- Обе реализации `VoiceProvider` взаимозаменяемы: переключение в настройках без перезапуска. Игровая логика и тесты этапов 1–8 не меняются.
- Облачный синтез озвучивает `reply` голосом из профиля агента; эмоция влияет на подачу.
- Встроенный синтез работает без сети на Android-планшете и Windows.
- Распознавание: облачное или через Gemini (`stt_mode = gemini_audio`, расшифровка возвращается отдельным полем и попадает в историю). Встроенное — если удалось подключить, иначе пункт неактивен.
- Разрешение микрофона запрашивается при первом нажатии; отказ даёт понятное сообщение, текстовый ввод остаётся.
- Ошибки голоса не ломают ход.

**Не делать:** клонирование голосов, 3D, синхронизацию губ.

## Шаблон задачи для Cursor

Скопировать, подставить номер этапа и отправить агенту:

```
Репозиторий: o5wtf/Detective, ветка main. Игра — детектив-допрос на Godot 4.7 (GDScript), Android (планшет) и Windows, ИИ через Gemini (каждый игрок вводит свой ключ в настройках).

Задача: выполнить Этап {N} «{название}» из docs/IMPLEMENTATION_PLAN.md.

Прочитай перед началом:
- docs/IMPLEMENTATION_PLAN.md — раздел этапа {N} и «Общие правила»;
- docs/ARCHITECTURE.md;
- разделы, указанные в «Следовать» этапа {N} (диздок — файл «Дизайн документ Игры» в корне; docs/LLM_PROTOCOL.md; docs/UI_PROTOTYPE.md).
Не читай cases/*_NOTES.md.

Требования:
- Делай только этот этап. Всё из пункта «Не делать» — не трогай.
- Godot 4.7.x, GDScript со статической типизацией, без сторонних аддонов.
- Не меняй диздок, cases/*.json и tools/validate_case.py. Если документы противоречат друг другу или чего-то не хватает — не придумывай, а опиши это в пулл-реквесте отдельным пунктом «Вопросы».
- Все тесты должны проходить: godot --headless --path . -s res://tests/run_tests.gd

Результат: пулл-реквест в main, в описании — что сделано, как проверено (вывод тестов), какие критерии приёмки выполнены (списком), что требует ручной проверки человеком.
```
